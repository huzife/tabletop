# 台球场景与物理模型

## 资源目录

有场景描述文件的台球模式必须把描述文件和球桌图片放在同一个模式目录中：

```text
games/billiards/scenes/
└── <mode>/
    ├── table.json
    └── table.png
```

当前中式八球使用 `scenes/chinese-eight-ball/table.json` 和同目录的
`table.png`。斯诺克还没有场景描述文件，暂时继续使用原有的程序化球桌与物理参数；
补齐斯诺克描述文件后再迁移，不为它创建占位 JSON。

新增或迁移一个模式时，还必须在 `physics/scene-registry.ts` 登记模式目录和 JSON
中的图片相对地址，并在 `physics/scene-assets.ts` 登记供浏览器打包的描述文件与图片
URL。构建产物会保留相同的 `scenes/<mode>/` 目录结构。

## 固定元素契约

每个台球 `table.json` 都使用 `tabletop.scene/v1`，并必须包含以下保留名称。这里规定的
是元素的 `name`，不是可自由命名的 `id`。

| `name`     | 数量 | 元素类型   | 用途与约束                                                 |
| ---------- | ---: | ---------- | ---------------------------------------------------------- |
| `table`    |    1 | `image`    | 球桌视觉背景；可见、无旋转、覆盖整个画布，不能是纯碰撞元素 |
| `boundary` |    1 | `polyline` | 球桌碰撞边界；闭合、无旋转，角色必须包含碰撞               |
| `hole`     |    6 | `ellipse`  | 六个落袋捕获区；无旋转，角色必须包含碰撞                   |

保留名称不能用于其他元素类型。其他视觉元素或标注可以保留，但不会参与权威物理计算。
具有描述文件的模式如果加载或校验失败，游戏不会退回旧版程序化球桌，以免展示模型和
碰撞模型不一致。

图片元素的 `source` 必须使用以 `./` 开头、相对于 `table.json` 所在目录的地址，例如：

```json
{
  "name": "table",
  "type": "image",
  "source": "./table.png"
}
```

源码、Node 构建产物和浏览器打包资源都由场景资源登记表绑定到这张同目录图片；JSON
本身不保存开发机路径或部署地址。

## 坐标与尺寸

台球场景采用 `top-left / right / down / scene-unit` 坐标系，`scaleMode` 为
`contain`。在台球模块中，一个 `scene-unit` 约定为一毫米：

- 画布宽高表示完整球桌的外沿尺寸。
- `boundary` 的上下长直边和左右长直边标定有效比赛区。
- 浏览器按同一标定绘制图片；Rust 物理核心按同一标定把边界和球洞转换为米。
- 游戏状态中的球坐标仍以米为单位，原点位于有效比赛区左下角，Y 轴向上。

设边界标定为 `left / right / top / bottom`，有效比赛区为 `playWidth /
playHeight` 米，则场景点到物理坐标的转换是：

```text
xMetres = (xScene - left) / (right - left) * playWidth
yMetres = (bottom - yScene) / (bottom - top) * playHeight
```

中式八球当前使用以下权威尺寸：

| 项目         | 尺寸                                         |
| ------------ | -------------------------------------------- |
| 完整球桌画布 | `2830 × 1550 mm`                             |
| 有效比赛区   | `2540 × 1270 mm`                             |
| 边界标定     | `left=145, right=2685, top=140, bottom=1410` |
| 球径         | `57.15 mm`                                   |

因此中八场景中一毫米恰好对应物理模型的一毫米；图片、边界、球洞与球的比例保持一致。

## 加载流程

Node 服务加载台球物理模块时会读取所有已登记的 `table.json`，先执行通用场景校验和
台球固定元素校验，再把完整描述传给新实例化的 WASM 核心。创建对局、规则判定、球桌
规格和每次击球模拟都从该实例中的场景几何生成。

浏览器加载台球模块时会同时启动场景描述文件和 WASM 的加载。校验完成后，描述文件被
配置到浏览器 WASM 实例；游戏视图从同一个缓存场景加载 `table` 图片。加载完成前只显示
加载状态，不先绘制旧版球桌。

由此，展示与物理模拟共享同一份 `table.json`：

```text
table.json
├── table    → 浏览器球桌背景
├── boundary → WASM 球与库边碰撞
└── hole × 6 → WASM 落袋检测
```

修改场景尺寸或几何后，应同步更新物理协议版本，并运行台球原生测试、TypeScript
类型检查、台球测试和生产构建。中八加载器还会拒绝无法映射到上述权威外沿尺寸的场景。
